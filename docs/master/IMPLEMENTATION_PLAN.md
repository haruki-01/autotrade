## 2. Bybit から BTC-USDT 過去データは取れるか？

**取れる。** しかも検証用途なら **APIキー不要**。

| 項目 | 内容 |
|------|------|
| API | Bybit v5 `GET /v5/market/kline`（公開） |
| 銘柄 | `BTCUSDT` / `category=linear`（USDT無期限） |
| 足 | `1d` / `4h` / `15m`（本プロジェクトで使用） |
| 認証 | 過去ローソク足の取得だけなら不要 |
| 本リポの実装 | `BybitPublicClient.fetch_klines` + `autotrade fetch-data` |
| 保存先 | `data/cache/*.csv`（gitignore） |

注意:
1. **Cloud Agent 環境からは国制限で 403** になることがある → **手元 Cursor / 自宅PC / VPS** で `fetch-data` する
2. 一度取得すれば CSV キャッシュされるので、同じ期間の再取得は不要
3. 履歴の長さは Bybit 側の保持範囲に依存（足りなければ期間を分割して取得）

→ **過去検証（バックテスト）用データとしてそのまま使える。**  
　Set B は実施済み（FAIL）。次は `MARKET_EDGE_MAP.md` の L-COST → L-MOM-VOL → L-BREAK。

### 月50エントリー要件の追加（2026-08-24）— SH系は打ち止め

指示により **入口判断は1分〜15分足・月50エントリー以上**を条件に追加した。
`min_trades: 100`（測れるか＝判定保留の床）とは**別の軸**の要件
（回す価値があるか＝不合格ライン）として `configs/eval_v3_btc.yaml` に宣言。

**SH-01 は 1.6〜1.8回/月で28〜31倍足りない。** 原因は頻度そのものではなく保有時間で、
中心設定の保有は中央値106時間・平均175時間。1枠で月50回には平均14.4時間以下が必要。
保有175時間で月50回を撃つには12.1枠＝証拠金364 USDT で元本300を超える。
**日足規模のトレンド追随と月50回は同じ口座で両立しない。** SH系は打ち止め。

コストの構造は要件に対して一部有利。年600回だと年間81 USDT（元本の27%）を払うが、
年20%に必要な純EVは **+0.100** で、月2回のロジックが必要とする +2.0 よりずっと低い。
頻度が上がると1回あたりの要求水準は下がる。

ただし実測のフロンティアは厳しい。記録済み1080件を頻度帯で切ると、
**EVプラスの割合が 74%（月10回未満）→ 2%（月50回以上）に崩れる**。
月50回以上の54件でプラスは1件（+0.004）のみ。必要な +0.067 に届かない。
これは 0.135 USDT/回のコストの床が頻度で薄まらないため。
ただし**この帯を狙って設計したロジックは258本中1本もない**ので、上限ではなく未着手。

**次の3つ。** 1と2は前提条件。

1. **約定モデル** — 指値の未約定を数える。入口メイカーで年間コスト 81 → 51 USDT、

2. **複数枠** — `engine.py` は1枠のみ（`position is None` でのみ建玉）。
   月50回 × 保有48時間なら3.3枠（証拠金100）で足りる
3. **月50回帯で設計** — 15分足ATR中央値 0.23〜0.32% の1〜1.5倍を取りに行く形

### 固定ブラケット枠での検証（2026-08-25）→ 比と幅を最適化

指示により枠を固定した。当初は RR 1:2・決済率90%。値幅の実測で損切り0.35%/利確0.70%。
その後「決済率90%は仮置き、比と幅は変数」と改訂されたので総当たりし、
**現行は 1:1.5 / 損切り0.70% / 利確1.05% / 入口指値**（決済率70%）。正本は
[BRACKET_FRAME.md](../hypothesis/BRACKET_FRAME.md)。

必要上振れの導出:

```
w* - w0 = (c/s) / (1 + RR)
θ ≥ 2c / (s² · RR)          必要なシグナル強度は幅の2乗に反比例
損切り × (1+RR) ≲ 1.35%     6時間でブラケットが機能する条件
```

指値のリスクは実測した。現値・1本待ちの約定率99%、逆選択は観測されず
（有利側に置いても勝率は下がらない）。損切りだけ成行。往復コスト 0.0730%。

旧枠（1:2, 0.35%, 両側テイカー）の必要上振れ +16.9pt に対し、
現行は対照基準で **+7.4pt**。15分足OHLCV 25条件×3期間、197,301トレード:

| 最大上振れ | +1.5pt | **+3.9pt**（`br_runs_5`, z=+4.07） |
| 必要に対する到達 | 9% | **53%** |
| 多重検定後に残った | 0 | **3本**（すべて順張り） |
| 黒字 | 0 | 0 |

**情報が無いのではなく、足りない。** 残り +3.3pt。
OHLCV以外（OI/funding/basis/taker）も同じブラケットで7条件を回したが、
最良でも +0.9pt（`br_fund_cheap`）。混み合いに乗るのは明確に負け（z=−6.35）。
`br_runs_5` に funding 安い側フィルタを足す one-point は勝率が動かず頻度だけ落ちた。

### 目標からの逆算モデル（2026-08-24）

月次ROI目標とDD上限から必要スペックを逆算する枠組みを追加。正本は
[TARGET_MODEL.md](./TARGET_MODEL.md)、計算は `scripts/target_feasibility.py`。

```
ROI / DD = 2 × N × Q²        Q = 1回のEV / 1回の標準偏差
```

**サイズを2倍にすると ROI も DD も2倍になるので、比はレバレッジ・証拠金・元本では
一切動かない。** 「月○%をDD△%以内で」の可否は Q と N だけで決まる。
月次シャープも `√(ROI/2DD)` で固定される。

BTC単独・3期間プールでの実測の最良は N×Q² = **0.179**
（`sh01_tp4_delay_1h`、月3.8回、Q=0.218、t=+2.80）。

| 目標（元本基準） | 必要 N×Q² | 必要回数/月 | 年率シャープ | 実測との差 |
|---|---|---|---|---|
| 月12% | 0.30 | 6 | 1.9 | **2倍** |
| 月120% | 3.00 | 63 | 6.0 | 17倍 |

**「月120%」の解釈で答えが10倍変わる。** 元本300基準なら月360 USDT（複利で年11,700倍、
水準として成立しない）。証拠金30基準なら月36 USDT ＝ 元本比12% で、実測との差は2倍。
**どちらの意味かの確認が必要。**

「保有14時間」は設計ではなく制約。1枠のエンジンで月50回なら 720÷50=14.4時間。
同じ数字がレバ3倍上限からも独立に出る（日足ATR損切り・N=75 で19.2時間）。

**最大の問題は Q が頻度と逆相関すること。** 実測の Q 中央値は月10回未満で 0.14〜0.19、
月25回超で 0.01〜0.02。N を増やすと Q が落ちるので積が増えない。
**Q を保ったまま N を増やす方法を見つけることが課題そのもの。**
