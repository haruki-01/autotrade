# 目標から必要スペックを逆算する

「月次ROI ○% ／ 分散は △ 以下」を決めると、1回あたりのEVと必要取引回数は
自由に選べなくなります。その関係をここに置きます。
数字は `scripts/target_feasibility.py` で再計算できます。

```
python scripts/target_feasibility.py --roi 120 --dd 20
```

## 使う関係は3つ

```
月次ROI = e × N / E          e = 1回のEV(USDT), N = 月の回数, E = 元本
最大DD  ≈ s² / (2e)          s = 1回の標準偏差
枠数    = N × H / 720        H = 平均保有時間(h)
```

2番目はドリフト付きランダムウォークの期待最大DDです。実測で検算すると、
SH-01（e=0.99, s=4.93）で s²/(2e) = 12.3 USDT = 元本の4.1%。
実測DDは期間ごとに 2.8 / 5.3 / 7.6%（平均5.2%）なので、目安として使えます。

## いちばん大事な帰結: サイズは答えにならない

上2つを割ると、サイズが消えます。

```
ROI / DD = 2 × N × Q²        Q = e/s（1回あたりのシャープ）
```

ポジションを2倍にすれば ROI も DD も2倍になるので、**比は動きません**。
「月○%をDD△%以内で」の可否は、**レバレッジ・証拠金・元本では一切変わらず**、
1回あたりの質 Q と月の回数 N だけで決まります。

```
必要条件:  N × Q² ≥ ROI / (2 × DD上限)
```

サイズは、この条件を満たしたあとに絶対水準を合わせるつまみにすぎません。

さらに、この形だと**月次シャープが Q と N の組み合わせに関係なく固定**されます。

```
必要な月次シャープ = √(ROI / 2DD)
```

## 目標水準ごとの要求スペック

DD上限 20%、BTC単独・3期間プールでの実測 Q = 0.218 を前提にした場合。

| 月次ROI | 必要 N×Q² | 必要な回数/月 | 必要月次シャープ | 年率換算 | 実測との差 |
|---|---|---|---|---|---|
| 12% | 0.30 | 6 | 0.55 | 1.9 | **2倍** |
| 30% | 0.75 | 16 | 0.87 | 3.0 | 4倍 |
| 60% | 1.50 | 32 | 1.22 | 4.2 | 8倍 |
| **120%** | **3.00** | **63** | **1.73** | **6.0** | **17倍** |

実測は月3.8回・Q=0.218（`sh01_tp4_delay_1h`、BTC単独3期間プール、t=+2.80）で
N×Q² = **0.179**。

## 「月120%」の解釈で答えが10倍変わる

現在のサイジングは証拠金30 USDT × レバ3（`sizing.mode: fixed_margin`）、元本300 USDT。
どちらを分母にするかで要求が桁で変わります。

| 解釈 | 月の利益 | 必要 N×Q² | 実測0.179との差 | 必要な回数/月 |
|---|---|---|---|---|
| 元本300に対して120% | 360 USDT | 3.00 | 17倍 | 63 |
| 証拠金30に対して120% | 36 USDT | 0.30 | **2倍** | **6** |

後者は元本比で月12%です。**前者は複利で年11,700倍**（300 USDT が1年で350万 USDT）
になるので、水準として成立しません。**どちらの意味かを確認する必要があります。**

## 「保有14時間」はロジックではなく制約

前回の14.4時間は設計思想ではなく割り算です。

- **1枠しか持てないエンジンで**月50回撃つなら、720時間 ÷ 50 = **14.4時間**しか
  1回に使えません。`engine.py` は `position is None` のときだけ建玉を作ります。
  取引所側も、サブ口座なしでは BTCUSDT 無期限を独立チケットとして持てません
  （Bybit one-way はネット1本、hedge でも long+short の2本まで）。
  詳細は [BRACKET_FRAME.md](../hypothesis/BRACKET_FRAME.md) の「1口座で複数ポジションは可能か」。

同じ数字が、ROI目標とレバレッジ上限からも独立に出ます。必要レバは枠数に比例するので:

```
必要レバ = (N × H / 720) × (許容損失 / 損切り幅) / 元本
```

月120%・Q=0.20・N=75、EVが許容損失の20%（=0.20R）とすると許容損失は24 USDT。
レバ3倍以内に収まる保有時間の上限は:

| 損切り幅 | 幅(%) | 枠数の上限 | H上限（N=75） | H上限（N=200） |
|---|---|---|---|---|
| 15mATR × 1.5 | 0.41% | 0.15 | 1.5h | 0.6h |
| 1hATR × 1.5 | 0.97% | 0.37 | 3.5h | 1.3h |
| 4hATR × 1.5 | 1.98% | 0.74 | 7.1h | 2.7h |
| 1dATR × 1.5 | 5.32% | 2.00 | **19.2h** | 7.2h |

**14〜20時間という数字が2つの独立な経路から出てきます。** 偶然ではなく、
どちらも「限られた元本で回数を稼ごうとすると1回に割ける時間が短くなる」
という同じ制約を別の角度から見ているだけです。

## そして短く持つとコストが効く

許容損失を固定してサイズを損切り幅で決めるので、コスト比は幅だけで決まります。

```
往復コスト / 許容損失 = 0.150% / 損切り幅
```

| 損切り幅 | 幅(%) | コスト/許容損失 | 純EV 0.20R に必要な粗EV |
|---|---|---|---|
| 15mATR × 1.5 | 0.41% | **36.4%** | 0.56R |
| 1hATR × 1.5 | 0.97% | 15.4% | 0.35R |
| 4hATR × 1.5 | 1.98% | **7.6%** | 0.28R |
| 1dATR × 1.5 | 5.32% | 2.8% | 0.23R |

短く持つほどコストが許容損失を食い、長く持つほど枠が足りません。
**4時間ATR 前後が両者の妥協点**です。

## 実測の Q は頻度を上げると落ちる

記録済み全ラン（勝率とペイオフから σ を復元。σ を2〜15%低く見積もるので Q は楽観側）。

| 頻度帯（回/月） | EV+の記録数 | 最良Q | Q中央値 |
|---|---|---|---|
| 0〜5 | 178 / 253 | 0.534 | 0.135 |
| 5〜10 | 165 / 223 | 0.361 | 0.185 |
| 10〜25 | 75 / 235 | 0.205 | 0.060 |
| 25〜50 | 5 / 97 | 0.041 | 0.014 |
| 50〜100 | 1 / 52 | 0.004 | 0.004 |
| 100+ | 0 / 2 | — | — |

**これが最大の問題です。** 必要条件 N×Q² は N を増やせば満たせますが、
実測では N を増やすと Q が落ちるので、積が増えません。
**Q を保ったまま N を増やす**方法を見つけることが課題そのものです。

## この枠組みで何が変わるか

判定が「EVがプラスか」から「N×Q² が目標に足りるか」に変わります。
EVプラスでも N×Q² が足りなければ目標に届かないので、単一の数字で比較できます。

- `min_trades: 100` — 測れるか（サンプル数の床）
- `min_trades_per_month: 50` — 回す価値があるか（運用要件）
- **`N × Q² ≥ ROI/(2·DD)`** — 目標に届くか（この文書）

3つ目を実装する前に、目標ROIの解釈（元本基準か証拠金基準か）を確定する必要があります。
