# バックテスト設計 v1

## 1. 目的

仮説 v1（日足フィルタ × 4Hフィルタ × 15mエントリー）が、  
**手数料・スリッページ控除後に期待値プラスになりうるか**を、再現可能な手順で判定する。

「検証OK」はバックテスト合格だけでなく、その後の **demo（遅延・レート制限含む）** まで含めて初めて仮確定とする。

## 2. 対象

| 項目 | 値 |
|------|-----|
| 取引所 | Bybit |
| シンボル | BTCUSDT（USDT無期限） |
| 足 | 1D / 4H / 15m（同一期間を揃える） |
| レバ（シミュ） | 3倍固定（感度確認で2と5も参考表示可） |
| 初期資金（仮想） | 例: 10,000 USDT（相対比較用。絶対額は後で変更可） |

## 3. データ仕様

### 3.1 取得

- Bybit 公開ローソク足 API（バックテスト段階では秘密鍵不要）
- フィールド: `open, high, low, close, volume, start_time`
- タイムスタンプは UTC で統一

### 3.2 期間（案）

全体を3つに分ける（未来情報の混入を防ぐ）。

| セット | 期間イメージ | 用途 |
|--------|--------------|------|
| A. 学習/調整 | 直近のさらに前〜中期（例: 2022-01 〜 2023-12） | ルールの穴埋め・仮パラメータ確認（いじりすぎ禁止） |
| B. 本検証 | 例: 2024-01 〜 2024-12 | **合否の主判定** |
| C. 直近確認 | 例: 2025-01 〜 取得可能な最新 | 相場変化への耐性チェック |

※ 正確な開始日はデータ取得後に「足りる本数があるか」で確定する。  
　重要なのは **本検証期間の成績だけでパラメータを再最適化しない**こと。

### 3.3 マルチタイムフレームの扱い

- 判定は **足が確定してから**（未確定足の終値は使わない）
- 15mの時刻 T でエントリー判断するとき:
  - 使える日足: T 以前に確定した最新の1D
  - 使える4H: T 以前に確定した最新の4H
- ルックアヘッドバイアス禁止（未来の確定足を見ない）

## 4. コスト・約定モデル（必須）

実戦との完全一致は狙わないが、**甘いゼロコスト検証は禁止**。

| 項目 | v1仮定 | 備考 |
|------|--------|------|
| 手数料 | 往復で保守的に設定（例: taker 0.055% × 2 = 0.11%） | Bybitの実レートに合わせて更新 |
| スリッページ | エントリー/決済それぞれ **0.02%** | 成行想定の簡易モデル |
| 資金調達率 | v1は **無視 or 低頻度概算** | 後で精度上げる。まず手数料+スリッページ優先 |
| 部分約定 | なし（全量約定と仮定） | 少額前提 |
| レイテンシ | バックテストでは **次足オープンで約定** | 15m確定後、次の15mで執行とみなす |

執行タイミング（v1）:

```text
15m足が確定 → シグナル判定 → 「次の15mの始値 ± スリッページ」で約定
```

これにより「確定足の終値ぴったりで約定」する楽観を避ける。

## 5. 戦略ロジックの実装対応表

詳細ルールは [HYPOTHESIS.md](./HYPOTHESIS.md)。バックテストコードが守るべき対応:

| モジュール | 入力 | 出力 |
|------------|------|------|
| DailyTrend | 1D OHLCV | Long / Short / Neutral |
| H4Trend | 4H OHLCV | Long / Short / Flat |
| Entry15m | 15m OHLCV + 許可方向 | EnterLong / EnterShort / Hold |
| Exit15m | 建玉 + 15m/4H | Stop / TakeProfit / TrendBreak / Hold |
| Portfolio | 残高・レバ・リスク% | 注文サイズ |
| Accounting | 約定・手数料 | 残高、トレード台帳、DD |

## 6. 出力メトリクス（必須）

毎ランで必ず出す:

**主指標**
- 期間リターン（%、必要なら月次換算）
- トレード数
- 1トレードあたり平均損益（USDT と %）
- 期待値の式: `平均損益 ≈ 月次利益率の材料`（月間回数 × 平均損益）

**ガードレール**
- 最大ドローダウン %
- 勝率（参考。単独最適化しない）
- 平均利益 / 平均損失（ペイオフ比）
- 連続最大損失回数
- 手数料総額（コスト感度の確認用）

**内訳**
- Longのみ / Shortのみの成績
- 月次リターン一覧（どの局面で効いたか）

## 7. 合否判定（ゲート）

### Gate BT-1（バックテスト本検証セット B）

すべて満たしたら「バックテスト合格候補」:

1. コスト控除後の **総期待値がプラス**（平均トレード損益 > 0）
2. トレード数 **≥ 100**（満たない場合は判定保留。期間延長を検討）
3. 最大DD **≤ 20%**
4. 月次換算リターンがマイナス月ばかりでない（例: 半分以上の月が極端な崩壊でないこと — 詳細閾値は初回結果後に固定）

### Gate BT-2（直近セット C）

- セットBで合格したパラメータを **変えずに** Cへ適用
- 期待値の符号が維持、または大きく崩壊していないこと  
  （例: 平均トレード損益がBの半分以下かつマイナスなら要再検討）

### Gate DEMO（バックテスト後）

バックテスト合格後に実施。設計に含めておく項目:

- testnet で同一シグナルが注文まで届く
- レート制限エラーの有無とリトライ
- 再接続後にポジション認識がずれない
- メンテ時間帯の振る舞い（新規停止 or 安全側）

DEMO不合格なら live に進まない。

## 8. パラメータ方針（過学習防止）

v1で触ってよい候補（少数）:

| パラメータ | 初期値 | 触る範囲の例 |
|------------|--------|----------------|
| 日足EMA | 50 | 40 / 50 / 60 程度まで |
| 4H EMA | 20 | 15 / 20 / 25 |
| 15m EMA | 20 | 固定推奨 |
| 損切り | 1.0% | 0.8 / 1.0 / 1.2 |
| 利確 | 1.5% | 1.2 / 1.5 / 2.0 |
| レバ | 3 | 合否はレバ3で判定。2と5は参考 |

禁止:
- グリッドサーチの大量探索
- セットBの結果を見てからセットB用に再最適化
- 指標を次々追加して曲線を合わせること

## 9. 実験ログ（再現性）

各バックテスト実行で残す:

- Gitコミットハッシュ
- データ期間（A/B/C）
- パラメータ一式
- コスト仮定
- メトリクス結果（JSONまたはCSV）
- トレード一覧CSV（entry/exit時刻、方向、損益、理由）

フォルダ案（実装時）:

```text
artifacts/backtests/<date>_<label>/
  config.json
  metrics.json
  trades.csv
  equity_curve.csv
```

## 10. 実行手順（オペレーション）

1. 1D/4H/15m データを取得・保存
2. 仮説v1の初期パラメータでセットAを通し、実装バグがないか確認（成績は参考）
3. **セットBで合否判定**
4. 合格ならセットCで耐久チェック
5. 合格候補のみ demo へ
6. demoで Gate DEMO を確認してから少額 live

## 11. 失敗時の次アクション

| 結果 | 次にやること |
|------|----------------|
| 実装バグ（未来参照など） | ロジック修正して再ラン |
| 期待値マイナス・浅いDD | エントリー条件を1点だけ変更して再検証 |
| 期待値プラス・DD深い | 損切り・サイズ・フィルタを見直し |
| トレード過少 | 15m条件が厳しすぎ。緩和は1点ずつ |
| トレード過多で手数料負け | フィルタ強化 or 利確/損切り見直し |
| Bは良いがCが崩壊 | 相場レジーム依存。仮説の前提を見直し |
