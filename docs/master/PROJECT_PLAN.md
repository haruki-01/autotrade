# 自動売買プロジェクト計画（Phase 1）

## 1. 目的

Bybit の BTC-USDT で、**勝てる自動売買 bot を1本**つくり、  
仮説 → バックテスト → デモ検証 → 少額本番 までを一連で通す。

この時点では Web UI / 複数 bot 管理は作らない。

## 2. 理想状態（将来）との関係

| 将来の理想 | Phase 1 でやること | 後回し |
|------------|-------------------|--------|
| 複数ロジックが稼働し収益 | 1ロジックで「勝つ型」を確立 | 2本目以降 |
| Dashboard で監視・ON/OFF | ログと数値ファイルで確認 | Webアプリ |
| ダミーデータで新ロジック検証 | 同一エンジンでバックテスト/デモ | UIからの検証画面 |
| Webで一元管理 | 対象外 | Phase 4以降 |

## 3. 確定事項

| 項目 | 決定内容 |
|------|----------|
| 取引所 | Bybit |
| 銘柄 | BTC-USDT（USDT無期限を想定、レバ利用のため） |
| レバレッジ | 2〜5倍 |
| bot数 | 1本 |
| UI | なし |
| 最優先 | 勝てるロジックの確立 |
| 時間足 | **日足=全体トレンド / 4時間=現在トレンド / 15分=エントリー** |
| 認証情報 | `secrets/demo` と `secrets/live` に分離 |
| 板・自己影響 | 今は検討しない（少額・まず試す） |
| API遅延・メンテ・レート制限 | デモ以降の検証で必須確認 |

## 4. 成功の定義（仮）

主指標:
- **月次利益率**（手数料控除後）
- 内訳イメージ: `1トレード期待値 × 月間トレード回数`

ガードレール（不合格ライン・2026-08-25 確定）:
- 最大ドローダウン **20%超** → 不合格
- 手数料・スリッページ控除後に期待値がゼロ以下 → 不合格
- 評価期間のトレード数 **100回未満** → 判定保留（サンプル不足）。不合格ではない
- **月間エントリー数 50回** → **合否に使わない**（2026-08-24 に一度入れ、2026-08-25 に外した）
- **月120%** → 到達可能性の別軸。検証の合否ではない

トレード数100は**測れるか**（検証精度）の床。月50は「回す価値」の記録で、
SH-01 のような日足規模ロジックを落とす条件にはしない。
履歴: [月50エントリー要件](../hypothesis/postmortems/2026-08-24-trade-rate-requirement.md)

※ 月次「何%あれば成功か」の絶対目標は、第1回バックテスト結果を見て調整する。

**目標から必要スペックを逆算する枠組み**（2026-08-24）:
月次ROI目標とDD上限を決めると、1回あたりのEVと必要回数は自由に選べなくなる。

```
ROI / DD = 2 × N × Q²        N = 月の回数, Q = 1回のEV / 1回の標準偏差
```

サイズを2倍にするとROIもDDも2倍になるので、**比はレバレッジや証拠金では動かない**。
可否は Q と N だけで決まる。詳細と実測値: [TARGET_MODEL.md](./TARGET_MODEL.md)

## 5. フェーズ

### Phase 0 — 設計（本ドキュメント群）
- 全体プラン、仮説、バックテスト設計を固定する

### Phase 1 — コアエンジン（UIなし）
- データ取得（日足・4H・15m）
- シグナル判定
- 注文IF（モード: `backtest` / `demo` / `live`）
- 共通リスク制限（レバ上限、1日損失上限、最大ポジション）
- 実行ログ（シグナル・注文・約定・PnL）

### Phase 2 — バックテスト
- 仮説どおりのルールで過去検証
- コスト込み評価、期間分割、合否判定

### Phase 3 — デモ検証（testnet）
- 同一エンジンで実API注文（デモ資金）
- メンテ・レート制限・遅延・再接続を観察

### Phase 4 — 少額本番
- `secrets/live` のキー、出金権限なし、IP制限推奨
- 少額・厳しい損失上限で最終確認

### Phase 5 以降（本Phase外）
- 2本目ロジック、portfolioリスク、Dashboard、ON/OFF管理

## 6. アーキテクチャ方針（Phase 1）

```text
[Market Data] → [Signal (D/4H/15m)] → [Risk Check] → [Execution]
                      ↑                      ↑
                 同一コードパス         backtest/demo/live はモード差のみ
```

原則:
1. バックテストと実運用でロジック実装を分けない
2. デフォルト起動は `backtest` または `demo`（誤って live しない）
3. APIキーは環境別ファイルのみから読む（Git管理外）

## 7. リスク方針（共通）

- レバレッジ上限: 5倍（設定は2〜5）
- 出金権限なしのAPIキーのみ使用
- demo / live でキー分離
- live は明示フラグがないと起動しない
- 1日損失上限・最大ポジションをエンジン側で強制（後で数値確定）

## 8. セキュリティ

詳細は `secrets/README.md` を参照。

要点:
- 実キーは `secrets/**/*.env`（gitignore）
- demo と live を混ぜない
- ログにキーを出さない
- 漏洩時は即無効化 → 再発行

## 9. 非目標（今はやらない）

- Web UI / Dashboard
- 複数 bot 同時運用
- FX
- 秒足スキャルピング
- 高度な板シミュレーション

## 10. 成果物チェックリスト（Phase 1完了条件）

- [ ] 仮説ドキュメントに沿ったシグナル実装
- [ ] バックテストが再現可能に回る
- [ ] 合否が数値で出る（リターン、期待値、回数、DD）
- [ ] demo モードで一定期間稼働ログが残る
- [ ] live は鍵・フラグ・リスク制限なしでは動かない
