# 仮説の三層モデル（春希さんの定義を正とする）

最終更新: 2026-08-22

## 結論（合意）

**あなたの理解で合っている。**

```text
① トレードスポット仮説（何が起きやすいか）
      ↓
② 実装ロジック案（どう検知・執行するか）← 複数あってよい
      ↓
③ 検証（そのロジックの正しさ・費用後の期待値）
```

例（あなたの例）:

| 層 | 内容 |
|----|------|
| **① 仮説** | ダブルボトム後、ネックライン突破 → ネック付近で再反発すると、ロングに伸びやすい |
| **② ロジック①** | 〜のインジでボトムとネックを定義し、再反発を検知してロング |
| **② ロジック②** | 別インジ／複合で同じスポットを検知してロング |
| **③ 検証** | 各ロジックを実データ formal eval で測る |

以前の「ストック技法 A〜N」（マップ横断・Who-loses・自由度契約など）は、  
**①を考えるための発想法というより、①②③を壊れないように進めるための規律・衛生ルール**だった。  
それを守っても「勝てるスポット仮説」は自動では出てこない。指摘のとおり。

## 三層の定義

### ① トレードスポット仮説（Trade Spot Hypothesis）

**相場のどこで、何が起きやすいか**の主張。チャート／フローの言葉で書く。

- よい: 「ダブルボトム → ネック突破 → ネック再テスト反発 → 伸びやすい」
- 悪い: 「RSIとEMAが揃ったら買う」（これは②に近い）

必須の中身（短く）:

- **セットアップ**（形・イベント）
- **トリガー**（いつ入るか）
- **期待する動き**（どっちへどれくらいのイメージ）
- **崩れる形**（仮説が無効になるチャート）
- （任意だが推奨）誰が払っていそうか／どの歪みに近いか

ここが「筋のよさ」の本体。

### ② 実装ロジック（Logic / 実証案）

①を **機械が判定できる規則** に落としたもの。  
**1仮説に対してロジックは複数**あってよい（実証①②③…）。

- インジの定義、閾値、時間足、フィルタの組み合わせ
- 「同じスポットを別の測り方で捉える」比較が目的
- ロジックを足すたびに自由度・試行番号が増える（衛生はここで効く）

### ③ 検証（Validation）

②の各ロジックについて:

- 実データ・固定コスト・固定サイジングで測る（formal eval）
- 合否・棄却・学びを残す

①そのものを「インジなしで直検証」しにくい場合も多いので、  
実務上は **①を固定したまま②を変えて③する**のが本体になる。

## 以前の文書との関係（役割分担）

| 文書・概念 | 本来の役割 | 誤解しやすい点 |
|------------|------------|----------------|
| E1〜E8 歪みマップ | ①の**背景ラベル**・優先度 | 歪みID自体がトレード仮説ではない |
| Who loses / 自由度 / lock | ①②③を進める**規律** | 守るだけでは勝てる①は出ない |
| CREATION_FLOW | ①→②のカード化・ready まで | 「発想の源泉」ではない |
| VALIDATION_FLOW | ③の再現手順 | 仮説の中身を生まない |
| HYPOTHESIS_STOCK_METHODS | **規律・補充オペ**寄り | 「筋のいい仮説の作り方」と呼ぶのは不適切だった → 改名済み |

## フォルダの対応（運用）

```text
docs/hypothesis/
  spots/           ← ① トレードスポット仮説（本体のストック）
  inventory/       ← ② ロジック実証カード（spot に紐づく）※既存を流用可
  evidence/        ← ①の粗い裏付け or ②の事前スクリーニング
  craft/           ← フロー・規律・発想の補助
```

検証は従来どおり `eval/` + VALIDATION_FLOW。
