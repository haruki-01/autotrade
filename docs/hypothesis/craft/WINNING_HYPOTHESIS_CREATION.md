# 勝てる仮説の作り方（作成レイヤ専用）

最終更新: 2026-08-22  
対象: **仮説作成のみ**（formal eval・デモ実装は別レイヤ）  
位置づけ: 検証は「実験」。作成は「実験する価値のある主張を書くこと」。

---

## 0. 作成と検証を分ける（最重要）

| | **仮説作成** | **仮説検証** |
|--|--------------|--------------|
| 問い | なぜ儲かるか？誰が払うか？いつ死ぬか？ | その主張はデータで棄却されるか？ |
| 成果物 | 文章の主張 + 証拠メモ + 棄却条件 | formal eval / walk-forward / デモ |
| 成功 | 「測る価値がある」状態 | PASS/FAIL と学び |
| 失敗の典型 | インジから入る・物語を後付け | 作成が弱いのに測りまくる |

公開研究の共通メッセージ（QuantJourney 等）:

> *A trading strategy is a falsifiable claim about how markets misprice something… The claim comes first; the code is its experiment.*

**コードの前に主張。** 順序を逆にすると、どんなに良い検証器でも救えない（データはすでに「使い切られている」）。

本ドキュメントは左列だけを扱う。右列は `EVAL_PROTOCOL` / `backtest-eval` skill の領域。

---

## 1. 「勝てる仮説」の定義（検証前）

検証前に勝てると言えるのは、次を満たす主張だけである。

1. **経済的主張**がある  
   リスクプレミアム / 行動バイアス / 制度・構造制約のどれか。
2. **相手がいる**（who loses）  
   パターンだけではエッジではない。誰がなぜ負けを受け入れるか。
3. **死ぬ条件が書ける**（dies when）  
   混雑・コスト・レジーム変化で消えるシナリオ。
4. **先に棄却テストを約束できる**（testable）  
   「何が起きたら捨てるか」を数字・手続きで先書き。
5. **自由度が小さい**  
   試行回数が多いほど「当たり」は偶然になる（後述の多重検定）。

「過去BTが黒字」は作成の定義に入れない。それは検証の出力。

## 2. 公開知見から抽出した「作成の公理」

### 2.1 順序の公理（QuantJourney / 実務パイプライン）

安価な段階で殺し、高価な段階に進まない。

```text
Stage 0  経済的主張（誰が負けるか・いつ死ぬか・棄却テスト）
   ↓ ゲート: 文章が埋まらないなら停止
Stage 1' 粗い証拠（レバなし・イベント統計）※本ラボの evidence/
   ↓ ゲート: 方向・裾が費用に負けそうなら停止
—— ここまでが「作成」。ここから下が「検証」——
Stage 2  最小実装 → formal eval …
```

作成レイヤの出口ゲート: **inventory カードが `ready`**。  
検証レイヤの入口: workstream + `autotrade eval`。

### 2.2 エッジの3源泉（Chan 系の整理）

アイデア生成は「市場がどっちの性質か」から始める。

| 源泉 | 意味 | 個人BTC無期限での扱い |
|------|------|------------------------|
| **Momentum** | 継続・群衆追随 | E1。学術は主に**クロスセクション**（多コイン）。単一BTC時系列は**別途証拠必須**（Liu–Tsyvinski–Wu は多資産因子） |
| **Mean reversion** | 行き過ぎの戻り | トレンド年は危険。E2戻り・E3は「単独逆張り禁止」が前提 |
| **Structural / event** | 制度・強制フロー | E2清算、E3 funding、E8費用。**説明可能性が高い**ほど作成向き |

Chan の実務示唆: モメンタムと平均回帰はレジームが違う → **同一ルールに混ぜない**（作成時点でファミリーを1つに固定）。

### 2.3 相手がいない仮説は捨てる（QuantJourney）

> If you cannot fill in WHO LOSES, you are describing a pattern, not an edge.

例（作成不合格）: 「RSIが30で買う」— 誰が強制的に売らされているかが無い。  
例（作成合格候補）: 「日足高値更新後、損切・後追いフローが同方向を延ばす。早すぎる逆張り側が払う。」

### 2.4 試行回数は資産であり毒（Bailey & López de Prado）

- 同じデータで多数の案を試し「一番良いもの」を取る → **選択バイアス**
- Deflated Sharpe Ratio (DSR): 試行数・非正規性を織り込むと「見かけのSharpe」はしぼむ
- **作成側の対策（検証前にできること）:**
  1. 自由度を意図的に小さくする（パラメータ山を作らない）
  2. 試した仮説数を inventory に数える（隠さない）
  3. 「検証で触るノブ」を作成時点で1個以下に約束する

### 2.5 正直なOOSは地味（arxiv: Hypothesis-Driven Trading 系）

厳密な walk-forward 後のリターンは、SNSの「年利○%」より遥かに地味になりうる。  
作成の目標は「派手なBT」ではなく **棄却可能な単純主張**。地味でもメカニズムがある方が、検証後に生き残る。

### 2.6 暗号モメンタムの注意（Liu–Tsyvinski–Wu, JoF）

- 学術で強いのは **複数コイン横断のモメンタム因子**
- 単一 BTCUSDT の時系列トレンド追随は **同じ論文のコピーではない**
- 作成時に書くべきこと: 「クロスセクション知見を、単一銘柄のどの現象に翻訳したか」と「翻訳の弱点」

本プロジェクトの E1 証拠（ブレイク後リターン）は、その翻訳の第一歩。作成はここで止まらず、「捕捉ルールが大勝ちを切らないか」まで文章化する。

## 3. 仮説の生成エンジン（作成ワークフロー）

春希さん / エージェントが仮説を「作る」ときの固定手順。

### Step A — 歪みを1つ選ぶ（マップから）

`MARKET_EDGE_MAP` の E1〜E8 から **主歪み1つ**。  
副次はフィルタ候補としてメモするだけ（まだルールに入れない）。

個人が取りやすい順（作成優先の目安）:

1. **E8**（取引しない）— 負のエッジ回避。単独でも仮説になる  
2. **E1**（モメンタム）— 本命だが単一BTCは証拠必須  
3. **E6**（ボラ）— 方向ではなくサイズ/停止の仮説  
4. **E4/E5**（時間）— ゲート仮説  
5. **E2/E3/E7** — データが揃うまで `blocked`

### Step B — 5行仮説（コード禁止）

QuantJourney 型を本ラボ用に翻訳:

```text
CLAIM:      （何が誤価格／継続／強制フローか）
WHY:        （メカニズム）
WHO LOSES:  （誰がなぜ払うか）
DIES WHEN:  （混雑・コスト・レジームで消える条件）
TESTABLE:   （棄却テストを先に約束。作成時点では「何を測るか」まで）
```

埋まらない欄がある = **仮説未完成**。inventory に `draft` で置いて止める。

### Step C — 家族診断（Chan）

この主張は **momentum / mean-reversion / structural** のどれか？  
混ざっていたら分割する。混ぜた瞬間に自由度と解釈が壊れる。

### Step D — 捕捉の設計原則（まだ最小ルール）

作成段階で決めるのは「現象」、インジ名ではない。

| 良い | 悪い |
|------|------|
| 「確定した N 日高値更新のあとだけ追随」 | 「EMAとRSIが揃ったら」 |
| 「往復コストを超えられない見積もりなら取引禁止」 | 「パラメータはBTで決める」 |
| 「大勝ちを固定幅で切らない」 | 「利確1.5%で勝率を上げる」 |

E1 作成の鉄則（本プロジェクトの敗因から）:

- 利益は少数トレードに偏りやすい → **固定小利確は主張と矛盾**
- 回転が多いと E8 に負ける → **希少イベント性**を主張に書く

### Step E — 粗い証拠タスクを定義する（作成の一部）

検証（formal eval）に渡す前に、`evidence/` で何を見るかを書く。

例:
- E1: イベント後 N 日リターン分布（レバなし）
- E8: シグナル密度 × 往復コストの下限損失
- E6: 高/低ボラでの固定%損切ヒット率

**証拠の設計までが作成。** 数値を出す作業は作成の延長だが、合否ゲートではない。

### Step F — 自由度契約

作成カードに必ず書く:

- 触ってよいノブ: **0〜1個**
- 触ってはいけないもの: 期間、コスト仮定、ゲート、他ファミリーの混入
- これまでに同じ歪みで試した回数（inventory 参照）

### Step G — ready 判定

`QUALITY_CHECKLIST` 全項目。合格して初めて検証レイヤへ渡す。

## 4. 仮説の「良い／悪い」判定表（作成専用）

| 観点 | 良い仮説 | 悪い仮説 |
|------|----------|----------|
| 主張 | 誤価格・強制フロー・制度 | 「当たりそう」 |
| 相手 | 明示 | 不在 |
| 死ぬ条件 | 具体 | 「相場が変わったら」だけ |
| 複雑さ | 現象1つ | インジ5つのAND |
| コスト | 費用を超える物語 | 無視 or 後回し |
| レジーム | 効く相場・効かない相場 | 全天候幻想 |
| データ | 今ある／blocked 明記 | 無いのに ready |
| 試行 | 差分1点・数え済み | 同時に10案 |

## 5. 個人 bot 向け：勝てる仮説が生まれやすい場所

公開知見 + 本マップの交差。

### 5.1 優先して「作る」べき型

1. **希少イベントのモメンタム（E1）**  
   ブレイク／構造更新のあとだけ。大勝ちを残す退出。ショートはレジーム証拠が要る。  
2. **取引しない優位（E8）**  
   「いつ撃たないか」が本体。エントリー改善の前に回転の下限コストを見積もる。  
3. **ボラにサイズを合わせる（E6）**  
   方向予測ではなく、破産しない仮説。  
4. **セッションゲート（E4/E5）**  
   薄い時間に同じサイズで戦わない。

### 5.2 作ってはいけない型（作成時点で棄却）

- 秒足・板の初動競争  
- funding 単独逆張り  
- 「勝率最適化」を目的にした利確  
- 特徴量探索・LLMに指標を量産させる（多重検定装置）  
- クロスセクション論文を、証拠なしに単一BTCへ直輸入  

### 5.3 容量（capacity）の視点（Chan）

小資金（証拠金$30×レバ3）は **不利ではなく条件**:

- 希少イベントが取れる（板を動かさない）
- 逆に、高回転・タイトスプレッド依存は不利  
作成時に「このサイズで意味があるか」を書く。

## 6. 作成テンプレ（コピペ用・検証用語禁止ゾーン）

inventory 起票前の下書き。**ここには BT 結果を書かない。**

```markdown
## 作成ドラフト（検証禁止）

CLAIM:
WHY:
WHO LOSES:
DIES WHEN:
FAMILY: momentum | mean-reversion | structural
PRIMARY_DISTORTION: E?
TRANSLATION_NOTE: （学術/実務知見を単一BTCにどう翻訳したか／弱点）
COARSE_EVIDENCE_PLAN: （evidence で見ること）
MINIMAL_PHENOMENON_RULE: （インジ名ではなく現象）
DEGREES_OF_FREEDOM: 0 or 1（触るノブ）
PRIOR_TRIALS_SAME_DISTORTION: （何本目か）
WHY_NOT_H01_FAIL_MODE: （固定利確・過回転等をどう避けるか）
READY_BLOCKERS: （足りないもの）
```

## 7. 作成レイヤのKPI（検証PASS数ではない）

仮説ラボの健全性は次で測る。

| KPI | 意味 |
|-----|------|
| draft → ready の転換率 | チェックリストが機能しているか |
| ready 前棄却数 | 安い段階で殺せているか |
| 同一歪みの試行番号 | 多重検定の自覚 |
| WHO LOSES 欠落カード数 | 0が目標 |
| 「インジ名だけのCLAIM」数 | 0が目標 |

Formal PASS は検証KPI。作成が上手くなると、**検証に送る本数が減り、送ったものの質が上がる**。

## 8. 本プロジェクトへの適用（いま）

| 項目 | 作成レイヤの含意 |
|------|------------------|
| H01系 | 作成不合格の典型（歪みと矛盾する捕捉）。再作成禁止 |
| HYP-002 | 作成は「E1 + who loses + 大勝ちを残す」まで妥当。n不足は**検証の問題**だが、次の作成は「希少性を保ったままイベント定義を変える」主張が必要 |
| 次に作るべき | ① E8の「撃たない」主張の精緻化 ② E1のイベント定義の別翻訳（例: 週次モメンタム、レジーム条件付き）③ E6サイズ仮説 — **いずれも文章と証拠計画が先** |

作成ミーティングのアジェンダ例（検証禁止）:

1. 歪みIDを選ぶ  
2. 5行仮説を埋める  
3. 家族診断  
4. 証拠計画  
5. 自由度契約  
6. ready / draft / blocked を決める
