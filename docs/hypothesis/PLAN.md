最終更新: 2026-08-22  
対象: 春希（PdM）＋エージェント  
前提: Formal eval Set B で 5本すべて FAIL（[`eval/reports/20260822-formal-eval-batch-setB.md`](../../eval/reports/20260822-formal-eval-batch-setB.md)）

## 0. 結論（先に）

**いま足りないのは「もう1本のインジ戦略」ではない。**  
足りないのは、**(1) 歪みが実データで存在する証拠** → **(2) その歪みだけを取るルール** → **(3) 費用後も残るか** の順で進める制度。

現状は (3) の測定器（formal eval）は整ったが、(1)(2) が弱い。だから「実装して測る」を繰り返しても、**構造的に負ける仮説**が増えるだけになる。

```text
やめる:  ロジック実装 → BT → FAIL → 別インジ
やる:    歪みの証拠 → 仮説カード合格 → 最小ルール → formal eval → 学び蓄積
```

**Formal eval が示した事実（採用判断に使う）:**

1. **押し目＋固定利確ファミリーは棄却**（H01 / L-COST）— E8 に負け、E1 の大勝ちを切る構造

3. **L-BREAK / H21 だけ期待値プラス** — ただし n 不足。**唯一の芽**だが「勝てると確定」ではない

根因仮説（メタ）:  
**「歪みの存在確認」を飛ばして「売買ルール」から入っている。**

## 2. 目標定義（仮説精度とは何か）

仮説精度が高い = 次を満たす確率が高いこと。

1. **メカニズムが書ける**（なぜズレるか、誰が払うか）
2. **レバなし・コスト前でも歪みの方向が見える**（イベント後リターン分布など）
3. **費用を入れてなお残る見込みがある**（往復コストより大きいエッジ）
4. **棄却条件が先に書いてある**（何が起きたら捨てるか）
5. **多重検定に負けない**（試行数を数え、単純な構造を優先）

「BT が黒字だった」は精度の定義に入れない（結果指標であり、仮説品質の定義ではない）。

## 3. 何をするべきか（優先順位付き）

### P0 — 制度（今週の土台）※本フォルダ

1. **仮説ラボ運用開始**（本ディレクトリ）
2. **実装前ゲート:** `craft/QUALITY_CHECKLIST.md` を通らない仮説は workstream に上げない
3. **敗因の型化:** Set B バッチを `postmortems/` に固定（同じ失敗を繰り返さない）

### P1 — 証拠ファースト（最重要の作業シフト）

ロジックを書く前に、歪みごとに **レバなしの粗い統計** を残す。

| 歪み | 先に測ること | 合格イメージ |
|------|--------------|--------------|
| E1 モメンタム | 日足ブレイク後 N 日のリターン分布、ロング偏り | 中央値 or 右裾が費用を超えうる |
| E6 ボラ | ATR 高低レジームでの損切ヒット率 | 固定%がレジームで壊れることの確認 |
| E8 費用 | 「シグナル密度 × 往復コスト」の下限損失 | 高回転案を自動棄却 |
| E2 清算 | （データ取得後）スパイク後の継続/戻り | 未着手でもカードは作れる |

成果物置き場: `evidence/E1_*.md` など。  
**証拠なしの「本命ロジック実装」は禁止。**

### P2 — 仮説カードの品質を上げる

新しい仮説は必ず `inventory/_template.md` から作り、最低限:

- 主歪み ID（E1〜E8）を1つ
- 負ける側（誰のフロー/癖を取るか）
- 必要データ
- **最小ルール**（パラメータは可能な限りゼロ）
- 棄却条件（数値）
- 既存 FAIL との差分（1点）

### P3 — 唯一の芽（L-BREAK）の扱い

いま実装チューニングしてよい候補は **Donchian 系だけ**（他は locked-fail）。

ただし精度向上の原則に従い:

1. 先に E1 の証拠メモ（ブレイク後リターン）を書く
2. 「n を増やす変更」は **1点だけ**（例: 日足→4H 確認後の執行）
3. 変更は新仮説カード（例: L-BREAK-v2）として inventory に置き、formal eval
4. Set B で黒字でも **Set C holdout** まで通すまで採用しない

### P4 — やらないこと（精度を殺す行為）

- 指標の AND 積み上げ・グリッドサーチ
- FAIL した押し目系のパラメータ再探索
- 合成 smoke を根拠にする
- 「勝率を上げる」最適化
- 同一 Set B での繰り返し再最適化
- AI に特徴量探索させる

### P5 — データ・取引所（並行だが後回しにしない前提）

- 研究は Vision で可。**採用前は Bybit（または実運用取引所）で再 lock**
- OI / funding / 清算が要る仮説（E2/E3）は、データパイプラインが無い限り inventory で `blocked` のまま

## 4. 新しい研究サイクル（運用フロー）

```text
[1] 歪みを選ぶ（MARKET_EDGE_MAP）
        ↓
[2] evidence/ に粗い統計（レバなし）
        ↓ 不合格なら棄却メモ
[3] inventory/ に仮説カード（チェックリスト合格）
        ↓
[4] workstream 作成 + 最小実装
        ↓
[5] autotrade eval（formal）
        ↓
[6] postmortems/ に学び（PASS/FAIL 問わず）
        ↓
[7] PASS のみ Set C → demo 検討
```

エージェント規約: 「検証して」と言われたら formal eval。  
「仮説を立てて／精度を上げて」と言われたら **本ラボを先に更新**し、チェックリスト不合格ならコードを書かない。
